# 方案 D：影子流程先行的 Strangler

## 架构

先让现有手写审批继续权威执行，同时把 requested/reviewed 事件镜像到 Flowable，生成只读轨迹并比较状态；不开放 Flowable 任务办理。比对稳定后，按租户/流程定义切换 authority：新申请由 Flowable 权威，旧实例仍走手写。

## 模块职责

平台除通用运行时外增加 shadow reconciler；HIS 增加 `his.workflow.mode=disabled|shadow|enforce` 路由和对账指标。enforce 阶段仍需采用 A/B/C 中的一种正式交互机制。

## 核心流程

shadow：手写动作 -> 既有事件 -> Flowable 镜像推进 -> 对账。enforce：以申请创建时记录的 approval mode 决定该实例始终走旧或新，不允许运行中换轨。

## 改动范围

早期小，完整切换后为中到大。它是最稳健的迁移策略，不是完整的长期消息架构。

## 扩展性

迁移扩展性高，可为每个新流程复用；运行时若长期保留双轨会增加认知负担。

## 实施成本

总工期最长，但单次发布风险最低，回滚最清晰。

## 已知弱点

- Shadow 无法验证真实并发抢办、权限拒绝和任务完成副作用，只能验证模型/轨迹等价。
- 双轨代码和指标若不设删除期限会永久化。
- 仍必须选择可靠的 enforce 数据面；不能单独作为最终架构。
